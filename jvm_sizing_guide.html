JVM Memory Sizing Guide

Thoras  ·  Using diagnostics to right-size JVM heap and container memory

What this guide does

JVM applications manage their own heap inside a Kubernetes container. Thoras observes the container's total memory working set, but the Java heap is a separate sizing concern. This guide uses your Thoras diagnostics to recommend four values:

  • JVM maximum heap (-Xmx or MaxRAMPercentage)
  • JVM initial heap (-Xms or InitialRAMPercentage)
  • Kubernetes memory request
  • Kubernetes memory limit
The script runs locally against files and values you provide. It does not connect to or modify your Kubernetes environment.

You can start with your Thoras diagnostics plus the current JVM flags and memory limit — no live JVM collection required. Optional jcmd measurements can refine the recommendation further. Sections 1–3 are everything you need for a first result.

The minimum mental model

A. What Thoras measures

The diagnostics package contains the selected container's historical working set — a container metric that approximates actively used resident memory at each sample point.

Observed container working set
├─ Resident Java heap
│  ├─ Live objects (retained after GC)
│  └─ Garbage and other touched heap space
├─ Resident JVM non-heap
│  ├─ Metaspace
│  ├─ Thread stacks
│  └─ Code cache, direct buffers, and native memory
└─ Other resident container memory

Each sample is an age-filtered per-pod fleet average — an average across eligible replicas at that timestamp, excluding newly started or recently terminated pods. Percentiles (p50, p90, p99, max) are computed over these fleet-average snapshots, not over individual pods. A workload with significant replica skew may have one pod consuming substantially more memory than the average suggests — validate with pod-level metrics if skew is a concern.

The basic recommendation sizes from the historical p99 and observed maximum of this total. The following are not part of the observed working set:

  • Unused heap capacity up to Xmx
  • Kubernetes memory request
  • Unused capacity between peak usage and the container limit
  • Safety headroom added by the analyzer

B. What the current configuration tells us

The JVM configuration defines two controls; Kubernetes defines two resource fields:

  • Xmx — the maximum Java heap the JVM may use
  • Xms — the initial heap at startup
  • Memory request — the amount Kubernetes accounts for when scheduling the pod
  • Memory limit — the enforced OOM boundary for the container

The basic calculation combines these with working-set history to recommend new values for all four.

C. What optional JVM measurements add

Two measurements from a live JVM can make the heap recommendation more direct:

  • Heap-used snapshot — a point-in-time measurement of Java heap after GC.run
  • Metaspace — class metadata stored outside the Java heap

These measurements do not replace Thoras diagnostics. The historical working set remains visible in the output as a sanity check.

D. What the analyzer adds

Safety headroom is intentionally unused capacity between expected peak consumption and the container limit. It is not observed memory — the analyzer calculates it and adds it to the recommendation.

How this guide produces a recommendation

Sections 1–3 are everything you need for this result. Sections 5–6 describe the optional JVM-measured refinement.

Input 1 — Diagnostics package

Download from the Thoras UI: open the workload, choose Export diagnostics, and save the zip file.

Pass it as: the first positional argument to the script.

Why: contains working-set history and the current memory request for the workload.

The script accepts any window length. Seven days or more gives the most representative percentiles; shorter windows still produce a recommendation with a note in the output.

Input 2 — Current memory limit

Run:

kubectl -n NAMESPACE get deployment/NAME \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="CONTAINER")].resources.limits.memory}'

Example output:

16Gi

The value you need is: the full string as printed.

Pass it as: --memory-limit 16Gi

Why: this is the container's current OOM boundary and the baseline for the comparison table.

Input 3 — Current JVM flags

Run:

kubectl -n NAMESPACE describe pod POD | grep -A5 JAVA_TOOL_OPTIONS

Or read them from your Deployment spec, environment variables, or ConfigMap if that is where they are set.

Example output:

JAVA_TOOL_OPTIONS: -XX:+UseG1GC -XX:MaxRAMPercentage=75.0 -XX:InitialRAMPercentage=75.0

The value you need is: the flag string (everything after the colon).

Pass it as: --flags="-XX:+UseG1GC -XX:MaxRAMPercentage=75.0 -XX:InitialRAMPercentage=75.0"

What does --flags mean?
--flags="..." passes the workload's current JVM configuration to the analyzer as text — it does not execute those flags or change your workload. Within that text, -XX:+UseG1GC is a JVM flag: the + enables the setting, and UseG1GC selects the G1 garbage collector. Thoras defaults were developed primarily around G1 workloads. When another collector is detected or the collector is unknown, the analyzer still produces a recommendation but displays a collector warning because the defaults are not separately calibrated for that collector. Copy the effective flags exactly — never add -XX:+UseG1GC merely to suppress the warning.

Why: the script uses these to detect configuration findings, identify the GC type, and derive the current heap configuration.

If no GC flag is visible in the supplied flags and you have independently confirmed G1GC (from GC logs or JMX), pass --assume-g1 to suppress the unknown-collector warning. This flag has no effect when a non-G1 collector is explicitly detected.

Input 4 — Container name (multi-container workloads only)

Run the script without --container first:

python3 analyze_jvm.py checkout-diagnostics.zip \
  --flags="-XX:+UseG1GC -XX:MaxRAMPercentage=75.0 -XX:InitialRAMPercentage=75.0" \
  --memory-limit 16Gi

If the diagnostics package contains multiple containers, the script lists them:

Multiple containers found in this diagnostics package:

  - istio-proxy
  - my-service

Re-run with: --container CONTAINER_NAME

The value you need is: the name of your JVM container.

Pass it as: --container my-service

Why: ensures working-set history and request come from the JVM container, not a sidecar.

How the basic calculation works

Without jcmd measurements, the analyzer knows the total container working set but cannot separate retained Java objects from garbage, metaspace, and other JVM memory. It therefore sizes the container limit from historical p99 and maximum usage, then derives Xmx by preserving the current heap-to-limit ratio — capped so the heap cannot consume the entire container.

Recommended limit =
    max(
        p99 working set × risk-profile margin,
        observed maximum × 1.05
    )

Current heap ratio =
    current Xmx ÷ current limit

Recommended Xmx =
    recommended limit × min(current heap ratio, 80%)
    leaving at least 300 MiB outside the heap

Recommended Xms =
    45% of recommended Xmx

Recommended request =
    min(historical p99 × risk-profile margin, recommended limit)
Risk margin adds capacity above historical p99 for normal variation and uncertainty in historical usage. Maximum floor preserves 5% above the highest observed sample. 80% heap cap preserves room outside the heap when JVM-native memory is not measured. 300 MiB fallback reserves space for all unmeasured memory outside the heap, including metaspace (unmeasured on this path). 45% Xms Thoras cost-oriented default for maintaining heap-size elasticity. Equal Xms and Xmx can favor latency consistency but reduce memory elasticity.

The request is sized from historical working set independently of the current request. The same p99 × margin used for the limit floor also drives the request, so both move together when the working set changes.

Step A — Find the Java PID

kubectl -n NAMESPACE exec POD_NAME -c CONTAINER -- jcmd -l

Example output:

1 /app.jar

The value you need is: the number at the left (the process ID).

Pass it as: PID in the commands below.

Why: identifies which Java process to query on the pod.

Step B — Read effective JVM flags (preferred flag source)

kubectl -n NAMESPACE exec POD_NAME -c CONTAINER -- jcmd PID VM.flags

Example output:

-XX:InitialHeapSize=12884901888 -XX:MaxHeapSize=12884901888 -XX:+UseG1GC -XX:MaxRAMPercentage=75.000000

The value you need is: the full flag string.

Pass it as: --flags="-XX:InitialHeapSize=12884901888 -XX:MaxHeapSize=12884901888 -XX:+UseG1GC -XX:MaxRAMPercentage=75.000000"

Why: VM.flags includes ergonomic defaults that may not appear in JAVA_TOOL_OPTIONS, giving the script a complete picture of the effective heap configuration.

Step C — Collect heap-used snapshot and metaspace

GC.run requests garbage collection. JVM behavior varies — it may pause the application, run concurrently, or be ignored. Treat the subsequent heap-used value as an estimate of retained heap. Run it only when a brief pause is acceptable for this workload. 
kubectl -n NAMESPACE exec POD_NAME -c CONTAINER -- jcmd PID GC.run
kubectl -n NAMESPACE exec POD_NAME -c CONTAINER -- jcmd PID GC.heap_info

Example output:

garbage-first heap   total 12582912K, used 4718592K [...]
Metaspace            used 196608K [...]

The values you need are:

  • Heap-used snapshot: 4718592K — the used value on the heap line
  • Metaspace: 196608K — the used value on the Metaspace line

Pass them as: --live-set 4718592K --metaspace 196608K

jcmd uses K to mean 1024 bytes (not 1000). The script accepts the value with the K suffix directly — do not convert it.

Why: these measurements replace working-set inference for Xmx and JVM-informed limit construction. Historical working set still sizes the request and validates the recommended limit.

Collect during representative load. Take several measurements and use the largest snapshot value. The pod and container must belong to the same workload as the diagnostics package.

Step D — Record the source pod

Pass it as: --jcmd-pod POD_NAME (use the same pod name from the commands above)

Why: recorded in the report so the recommendation can be traced back to its source measurements.

Full command with measurements

python3 analyze_jvm.py checkout-diagnostics.zip \
  --flags="-XX:InitialHeapSize=12884901888 -XX:MaxHeapSize=12884901888 -XX:+UseG1GC -XX:MaxRAMPercentage=75.000000" \
  --memory-limit 16Gi \
  --live-set 4718592K \
  --metaspace 196608K \
  --jcmd-pod checkout-6d8f9b-xk2pq

Use the flags copied from Step B exactly as printed. If the workload has multiple containers, add --container CONTAINER_NAME before the other arguments.

Before applying: resolve any active OOMKills or known material memory differences between replicas.

How the JVM-measured calculation works

With a heap-used snapshot and measured metaspace, the analyzer can size Xmx from retained heap demand and build the container limit from its components. Working-set history validates the result — if the recommended limit falls below 30% of the observed p99, the configuration is withheld.

Xmx  = heap-used snapshot × risk-profile multiplier
Xms  = Xmx × 45%

Container limit =
    Xmx
    + measured metaspace
    + non-heap fallback allowance (default 300 MiB)
    + Xmx × 12% safety headroom

Request =
    min(historical p99 × risk-profile margin, recommended limit)
300 MiB fallback reserves space for other unmeasured native/non-heap memory; measured metaspace is added separately. 12% headroom keeps modeled JVM consumption below the container's OOM boundary.
Risk profiles
ProfileWithout JVM measurementsWith heap-used snapshot
savingsp99 × 1.10snapshot × 2.0
balanced (default)p99 × 1.20snapshot × 2.5
reliabilityp99 × 1.30snapshot × 3.0

These multipliers and margins are Thoras policy starting points intended to provide a buffer for normal variation and uncertainty in historical usage. They should be calibrated against production outcomes — your account team can adjust them based on workload-specific behavior observed after rollout.

Most workloads should use balanced. Choose savings only when your organization intentionally accepts tighter margins. Choose reliability for workloads where a pause or restart is particularly costly.

Pass your choice as: --risk-profile savings or --risk-profile reliability

Reading the output

The comparison table

A request reduction frees schedulable capacity. A limit reduction changes the OOM boundary. Neither alone guarantees a cost reduction — that depends on node utilization and scheduling.

The configuration block

The block shows the values to apply to your JVM flags and Kubernetes resource fields. Update your Deployment manifest or ConfigMap — do not paste the block directly as YAML. Remove any conflicting -Xmx, -Xms, MaxRAMPercentage, or InitialRAMPercentage settings before applying.

When current flags were not supplied (--assume-g1 path), the comparison table shows Unknown for current heap values and N/A for those differences. Verify your actual flag configuration before applying the recommendation.

Historical-limit warning ladder

After calculating the recommended limit, the script compares it to historical p99 and maximum. The result determines whether the configuration is shown, qualified, or withheld:

ConditionSeverityBehavior
limit ≥ observed maximumNoneConfiguration shown without historical-capacity note
p99 ≤ limit < observed maximumHigh-water markConfiguration shown; note that an isolated peak above p99 would not be covered
30% × p99 ≤ limit < p99Staged validationConfiguration shown; staged deployment and monitoring required before broad rollout
limit < 30% × p99WithholdConfiguration withheld; candidate values shown for reference — reconcile inputs before applying

When no recommendation appears

  • No flags supplied: shows working-set statistics and analysis only. A JVM-measured recommendation can still be produced if --live-set, --metaspace, and --jcmd-pod are provided.
  • No memory limit supplied: prevents a diagnostics-only recommendation. JVM-measured sizing can still produce a recommendation, but the current memory-limit comparison will be unavailable.
  • Unknown or non-G1 collector: a recommendation is still produced, but a collector warning is displayed. Use --assume-g1 to suppress the warning when G1 is confirmed but no GC flag is visible in the supplied flags. Has no effect when a non-G1 collector is explicitly detected.
  • Withheld configuration: the recommended limit is below 30% of observed p99 — see ladder above. Verify the measurements came from the correct workload and rerun.

Apply the result

Apply the recommendation using your organization's standard staged deployment and rollback process. Memory limit changes require a pod restart to take effect.

Advanced overrides — usually leave these unchanged
OverrideDefaultPathWhen to change
--working-set-margin profile default both Affects the p99 limit candidate on the diagnostics-only path and the memory request on both paths. Decreasing it risks insufficient headroom; increasing it reduces savings.
--gc-multiplier profile default JVM-measured Choose a custom value within 2.0–3.0 when the three standard profile values are insufficient. Lower values increase GC pressure and collection frequency; higher values limit achievable savings.
--overhead-bytes 300 MiB both Minimum outside-heap allowance for thread stacks, code cache, direct buffers, and native libs. In JVM-measured mode, measured metaspace is added separately. Increase for native-heavy workloads; decreasing risks OOM from unmeasured native memory.
--headroom-ratio 12% JVM-measured You need a different container-level safety buffer above the calculated heap ceiling. Decreasing risks OOM under allocation spikes; increasing reduces savings.
--heap-style auto both You intentionally want absolute (-Xmx) or percentage (MaxRAMPercentage) output regardless of the current configuration style.
